# ЗАГАЛЬНІ ВИМОГИ ДО НАВЧАЛЬНОЇ ПРАКТИКИ

## 1. ОРГАНІЗАЦІЙНІ ВИМОГИ

### 1.1 Формальні вимоги

- Ознайомлення з технікою безпеки під час роботи з комп'ютерним обладнанням
- Обов'язкове відвідування занять з навчальної практики
- Отримання персонального індивідуального завдання
- Ведення щоденника практики протягом усього періоду
- Дотримання термінів подання звіту та його структури

### 1.2 Тривалість та структура

- Загальна тривалість: 3 тижні (15 робочих днів)
- Поділ на етапи: аналіз (1 тиждень), розробка (1 тиждень), інтеграція та захист (1 тиждень)

### 1.3 Звітність

- Щоденник практики (Додаток А)
- Звітна робота (Додаток В)
- Дисковий носій з проєктом та звітом підшитих в окрему папку
- Все це і в цифровому вигляді

## 2. ВИМОГИ ДО АНАЛІЗУ ТА ПЛАНУВАННЯ

### 2.1 Вибір теми та постановка задачі

- Вибір теми індивідуального проєкту (програма з графічним інтерфейсом)
- Аналіз предметної області
- Визначення проблеми, яку розв'язує програма
- Формулювання мети, завдань і очікуваних результатів розробки
- Оформлення початкового розділу звіту («Вступ», «Постановка задачі»)

### 2.2 Аналіз технологій та аналогів

- Визначення основних технологій розробки (мова програмування, СУБД, інструменти для UI)
- Аналіз аналогів програм
- Формування бізнес-логіки проєкту

### 2.3 Налаштування середовища розробки

- Налаштування інтегрованого середовища програмування
- Налаштування інструментів для роботи з базами даних
- Налаштування системи контролю версій (Git)
- Створення проєкту з використанням інструментів управління залежностями
- Підключення необхідних бібліотек

## 3. ВИМОГИ ДО БАЗИ ДАНИХ

### 3.1 Концептуальне моделювання (ОБОВ'ЯЗКОВЕ)

- Побудова концептуальної моделі «сутність-зв'язок»
- Створення ER-діаграми за допомогою графічних інструментів
- Визначення сутностей, їхніх атрибутів та взаємозв'язків

### 3.2 Логічна та фізична схема (ОБОВ'ЯЗКОВЕ)

- Розробка логічної схеми (опис таблиць та стовпців)
- Розробка фізичної схеми (конкретні типи даних)
- Мінімум 5 таблиць
- Реалізація зв'язків типу один-до-багатьох (1:N)
- Реалізація зв'язків типу багато-до-багатьох (N:M) через проміжні таблиці

### 3.3 Нормалізація (ОБОВ'ЯЗКОВЕ)

- Приведення таблиць до першої нормальної форми (1НФ)
- Приведення таблиць до другої нормальної форми (2НФ)
- Приведення таблиць до третьої нормальної форми (3НФ)

### 3.4 DDL-скрипти (ОБОВ'ЯЗКОВЕ)

- Створення DDL-скриптів для схеми бази даних
- Визначення первинних ключів (PRIMARY KEY)
- Визначення зовнішніх ключів (FOREIGN KEY)
- Визначення обмежень (NOT NULL, UNIQUE)
- Використання індексів для оптимізації запитів (CREATE INDEX)
- Використання транзакцій для забезпечення цілісності даних (BEGIN TRANSACTION, COMMIT, ROLLBACK)
- Використання тригерів для автоматизації операцій (CREATE TRIGGER) (при необхідності)

### 3.5 DML-операції та наповнення (ОБОВ'ЯЗКОВЕ)

- Реалізація DML-операцій для наповнення бази даних
- Наповнення бази достатньою кількістю тестових даних (реалістичних)
- Використання команди COMMIT для збереження змін

### 3.6 Збережені процедури (НЕ ОБОВ'ЯЗКОВЕ)

- Створення збережених процедур для базових операцій CRUD при необхідності

### 3.7 Віртуальні таблиці (НЕ ОБОВ'ЯЗКОВЕ)

- Розробка віртуальних таблиць (Views) для фільтрації та об'єднання даних при необхідності
- Використання INNER JOIN для отримання даних з кількох пов'язаних таблиць

### 3.8 Стиль коду SQL (ОБОВ'ЯЗКОВЕ)

- Забезпечення відповідності SQL-коду стандартам стилю
- Ключові слова у верхньому регістрі (SELECT, FROM, WHERE)
- Ідентифікатори у нижньому регістрі
- Використання snake_case для ідентифікаторів (хоча деякі СУБД можуть мати свої конвенції)

## 4. ВИМОГИ ДО АРХІТЕКТУРИ ПРОГРАМИ

### 4.1 Багатошарова архітектура (ОБОВ'ЯЗКОВЕ)

- Реалізація тришарової архітектури:
    - Шар даних (Data Layer)
    - Шар бізнес-логіки (Business Logic Layer)
    - Шар представлення (Presentation Layer)

### 4.2 Шар даних (ОБОВ'ЯЗКОВЕ)

#### 4.2.1 Визначення сутностей

- Визначення сутностей БД у класах
- Дотримання принципів ООП:
    - Інкапсуляція (private поля, public гетери/сетери)
    - Наслідування
    - Поліморфізм
    - Композиція

#### 4.2.2 Підключення до БД

- Налаштування підключення до реляційної бази даних
- Реалізація ефективного управління з'єднаннями (Connection Pool)
- Динамічне створення схеми та наповнення даними

#### 4.2.3 Мапінг даних

- Реалізація мапінгу даних між базою та програмою

#### 4.2.4 Патерни доступу до даних (ОБОВ'ЯЗКОВЕ)

- Застосування патерну Data Mapper
- Застосування патерну Repository
- Застосування патерну Lazy Initialization

#### 4.2.5 Валідація даних (ОБОВ'ЯЗКОВЕ)

- Забезпечення валідації даних на рівні шару даних

### 4.3 Шар бізнес-логіки (ОБОВ'ЯЗКОВЕ)

#### 4.3.1 Сервісні класи

- Визначення сутностей бізнес-шару
- Створення сервісних класів
- Інкапсуляція бізнес-логіки

#### 4.3.2 Патерни (ОБОВ'ЯЗКОВЕ)

- Реалізація патерну Dependency Injection (DI)
- Реалізація патерну Inversion of Control (IoC)
- Реалізація патерну Data Transfer Object (DTO)
- Застосування патерну Singleton
- Застосування патерну Facade
- Застосування патерну Proxy (при необхідності)
- Застосування патерну Builder (при необхідності)

#### 4.3.3 Додаткові функції (НЕ ОБОВ'ЯЗКОВЕ)

- Застосування аспектно-орієнтованого програмування (AOP) для логування або обробки транзакцій

#### 4.3.4 Валідація (ОБОВ'ЯЗКОВЕ)

- Забезпечення валідації бізнес-логіки

### 4.4 Шар представлення (ОБОВ'ЯЗКОВЕ)

#### 4.4.1 Графічний інтерфейс користувача

- Налаштування фреймворків для графічних елементів
- Розробка структури вікон та елементів управління

#### 4.4.2 Архітектурний патерн (ОБОВ'ЯЗКОВЕ)

- Реалізація архітектури для поділу логіки (наприклад, MVVM, MVC)
- Відокремлення логіки від виду

#### 4.4.3 Контролери (ОБОВ'АЗКОВЕ)

- Розробка контролерів для обробки подій
- Перенаправлення подій з UI у бізнес-логіку

#### 4.4.4 Реактивність (ОБОВ'ЯЗКОВЕ)

- Реалізація «біндінгу» даних
- Забезпечення реактивних елементів для динаміки інтерфейсу

#### 4.4.5 Асинхронність (ОБОВ'ЯЗКОВЕ)

- Забезпечення асинхронності в обробці операцій
- Уникнення блокування головного потоку UI

#### 4.4.6 Стилізація (ОБОВ'ЯЗКОВЕ)

- Забезпечення стилізації інтерфейсу (CSS або аналоги)
- Створення адаптивного користувацького інтерфейсу

#### 4.4.7 Валідація вводу (ОБОВ'ЯЗКОВЕ)

## 10. ОЦІНЮВАННЯ

### 10.1 Поточний контроль (до 70 балів)

1. Ознайомлення з програмою, вибір теми, постановка задачі, аналіз, налаштування середовища (8 балів)
2. Розробка моделі БД, ER-діаграм, нормалізація, DDL-скрипти, SQL (16 балів)
3. Налаштування шару даних, мапінг, патерни ООП, валідація (16 балів)
4. Тестування шару даних, розробка бізнес-логіки, інтеграційне тестування (10 балів)
5. Налаштування та програмування UI, MVVM, біндінг, асинхронність, рефакторинг (14 балів)
6. Звітність, документування, прототип, фінальне тестування (6 балів)

### 10.2 Підсумковий контроль (до 30 балів)

1. Якість звіту (15 балів):
    - Повнота, логічність структури
    - Наявність усіх розділів (вступ, зміст, висновки, додатки)
    - Дотримання вимог стандартів
    - Оформлення рисунків, схем, таблиць, нумерації, посилань

2. Захист практики (15 балів):
    - Володіння матеріалом
    - Чіткість відповідей
    - Демонстрація роботи програми
    - Аргументованість висновків

### 10.3 Критерії незадовільної оцінки

- Невиконання програми практики
- Неподання щоденника або звіту про практику
